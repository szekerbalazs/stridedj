# Decision log

Each row: what was decided, the options considered, and why. Interviewers ask "why X and not Y?" more than "what is X?".

| # | Decision | Options | Choice and why |
|---|---|---|---|
| 1 | LLM provider | OpenAI · Anthropic · self-hosted open model | **OpenAI**: prior experience with the SDK, and a mature Responses API with strict structured outputs and function calling. The provider sits behind an `LLMClient` port, so switching costs one adapter. |
| 2 | Agent framework | LangGraph / OpenAI Agents SDK / LiveKit Agents · hand-built | **Hand-built harness**: the loop is ~150 lines, and owning it means I can explain and test every decision (budgets, approvals, tracing). Frameworks hide exactly the parts interviewers ask about. |
| 3 | Agent shape | LLM-only intent parser + fixed workflow · autonomous agent · tool-calling agent with gated writes | **Tool-calling agent with read-only tools; writes only after human approval.** Flexible ("make it tomorrow morning instead") without giving the model the power to act. |
| 4 | Final answer format | free text · JSON in the prompt · strict structured outputs | **Strict structured output (`AgentReply`)**: the transport renders it with code, and evals grade it programmatically. |
| 5 | Chat transport | Telegram · Slack · WhatsApp | **Telegram**: a bot in 2 minutes, inline buttons, long polling (no public endpoint to secure). WhatsApp needs Meta business verification plus a public webhook. |
| 6 | Run data | Strava API · Garmin official API · `garminconnect` · intervals.icu · manual export | **`garminconnect` (live, unofficial)**, with intervals.icu as plan B and a synthetic source offline. Garmin's official API is partner-only. Strava's terms ban AI training on its data (2024) and reportedly its use in LLM context (2026). Unofficial APIs break (Garmin's March 2026 auth change broke `garth`), hence the `RunSource` port and the fallbacks. |
| 7 | Calendar reads | `events.list` · `freebusy.query` | **freebusy**: busy intervals without titles. Titles are private (who I meet) and untrusted (anyone can send an invite carrying instructions). |
| 8 | Secrets | `.env` · OS keychain · secret manager | **`.env` + `SecretStr`** for a single-user project; never logged, never shown to the LLM. A product would use a secret manager plus per-user encrypted token storage. |
| 9 | Project tooling | pip/venv · poetry · uv | **uv** (fast, a lockfile), **ruff**, **mypy --strict**, **pytest**, src layout. |
| 10 | HR zones | typed into `.env` · read from Garmin | **Read from Garmin Connect at startup** (RUNNING profile, else DEFAULT): one source of truth, so "Z2" always matches the watch. Garmin also returns time-in-zone per run, computed with the same zones. `.env` is only an override for non-Garmin sources. |
| 11 | Prompt changes | edit in place · versioned files + evals | **Versioned prompts** (`system_v1.md` … `system_v3.md`), compared with `run_eval.py --prompt`. v2 fixed one ambiguity found in transcripts ("6x800"); v3 (with new tool arguments) fixed named start times and interval totals found in live use; v4 added interval sessions and placeholders. No regressions. |
| 12 | Detecting interval sessions | Garmin lap structure · heart rate only · a CNN on the raw series · rules on pace + watch stops + heart rate | **Rules on three signals.** Laps are 1-km auto-laps unless a structured workout is used, so they hide reps and rests. Heart rate alone lags 20-60 s and has no samples while the watch is stopped. A CNN needs labels that didn't exist (a few dozen sessions at most) and couldn't be evaluated honestly. Pace finds the reps, watch stops (elapsed grows, timer doesn't) and slow stretches find the rests, the HR drop confirms them. Checked against hand-labelled runs; a learned model is the next step once there are enough labels. |
| 13 | Duration of an interval session | moving time · elapsed time · elapsed for every run | **Elapsed for intervals, moving for steady runs.** The rests are part of an interval workout (often with the watch stopped), so moving time books a slot that is far too short. A stop in a steady run is an interruption (a traffic light, a break); counting it would inflate every future estimate. |
| 14 | Calendar slot length | p80 + 10 min, rounded up to 15 · p80 + 5 min, rounded up to 5 · p80 + 5 min, rounded up to 15 | **p80 + 5, rounded up to the next quarter hour.** +10 min added up to 24 minutes on top of a time that already covers 4 runs in 5; 5-minute steps gave calendar entries like 18:30–19:40. Quarter hours keep the calendar tidy with less slack. |
| 15 | Uncertainty with few comparable runs | empirical quantiles only · a floor from the personal model | **Floor:** the p80 is at least the personal model's typical spread above the p50. Three runs can't show the spread, and an 80 % time equal to the expected time leaves no margin. |
| 16 | Choosing an interval session | the model describes options in text · buttons with options built in code | **Buttons, built in code.** Reps are distance-based, rests standing, target paces come from the runner's own sessions and adapt (faster after a clean session, unchanged after a miss or fade, easier after six weeks without that distance). The targets are recomputed from the runs, never stored. A tap becomes a code-made message, so the model plans with a session id, not with numbers it would have to copy. |
| 17 | Facts in the model's message | the model writes numbers (prompt rule) · placeholders · placeholders + a check against the plan | **Placeholders + check.** The harness attaches the plan (no id to copy) and fills `{start}`, `{expected}`… from it; any other number must be a fact of the plan or something the runner wrote. A first version banned every digit; the evals showed it mostly flagged "Z2" and correct echoes of the distance, so it became a check. A broken message is replaced, not retried: a stray digit must not cost the plan. |
| 18 | Playlist candidates and genres | everything in the library · own library first with a style floor · Spotify genres · Last.fm tags | **Own library first, a style floor, no spoken word; genres from Last.fm** mapped onto a closed list. Recommendations only fill gaps. Spotify returns no artist genres to development-mode apps, and Last.fm tags are crowd-written (untrusted), hence the closed list. Measured before/after with `scripts/playlist_quality.py`. |
| 19 | Learning the runner's taste | none · per-playlist rating · per-song rating | **Both:** 👍/👎 for the playlist (applies to its new songs) and a per-song 👎 toggle. Stored as ids only; disliked songs are never suggested again, liked ones count as favourites. |
| 20 | External rate limits | retry with a capped wait · fail fast and remember the block | **Fail fast + a circuit breaker.** A `Retry-After` of hours was retried after the 20 s cap, each retry hitting a blocked app. Now a long wait stops at once, and the Spotify client skips the API until the block has passed, across restarts. |
| 21 | Playlist variety | a rank penalty for recently used songs · no song of the last N playlists | **No song of the last 3 created playlists**, favourites included, matched by id and by title + lead artist (another version is the same song). Only a last-resort level lets the oldest one's songs back in, ranked lower, so the run is still covered. The penalty alone brought strong favourites back every time (40-55 % overlap with the previous playlist on the demo world). How many songs are new is the runner's pick per playlist: 0 / 50 / 100 % (`familiar` / `usual` / `discover`), by chat or with buttons on the card, which redraft only the playlist in code (no model call, a new approval token). |
| 22 | Genres that fit running | blocklist only · allowlist only · both | **Both.** A new song (not in the running playlists) needs a genre of the closed vocabulary, which holds running genres only; an artist whose top 3 Last.fm tags are on the blocklist (classical and soundtracks, ambient and relaxation, audiobooks and spoken word, jazz and blues, folk and acoustic, lo-fi and chillout, country) gets no genre. Exact tags only, so "blues rock" and "rhythm and blues" stay. Audiobook chapters are also caught by their title ("Kapitel 3"), before any lookup. The running playlists are exempt: the runner chose those songs. |
